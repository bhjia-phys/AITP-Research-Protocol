## Layout

```
suite/
  README.md               # how to run a session and score it (this spec, operational form)
  policy.md               # the semantic research-memory policy — hash-identical in both conditions
  adapters/
    cli.md                # I/O appendix: policy ↔ AITP CLI commands
    plain-files.md        # I/O appendix: policy ↔ plain markdown files, no aitp
  scenarios/
    S1-resumption.md      # script + expected-turn probes (seed lives in seeds/)
    S2-durable-events.md
    S3-heldout.md         # held out: not used for prompt/Skill iteration once the agent config is frozen
  seeds/
    S1/                   # portable seed: complete workspace fixture; copied fresh per run
    S2/
    S3/
  rubric.md               # metrics + pre-registered thresholds
  FROZEN.md               # pre-first-run freeze record; verified before the first scored run
  run-notes-template.md   # operator template; copy into runs/<date>/ and fill in by hand
  score-sheet-template.md # assessor template; copy and fill in during blind scoring
  gold/                   # assessor-side answers per scenario; NEVER in a seed or the agent-readable run env
  events/                 # operator-side turn-time event artifacts; NEVER in a seed or the initial workspace
    S2/                   # canonical artifacts injected at S2 turns 4 and 5 (Run protocol)
  runs/                   # per-run archive: transcripts, filled run notes, end states, score sheets (gitignored)
```

`policy.md` states WHAT to do (when to read memory, what counts as a durable
event, correction/contradiction handling, closeout discipline) with no
mention of tooling. Each adapter is a short appendix stating HOW the policy
maps to mechanics. The two conditions therefore run the same semantic policy;
only the I/O layer differs. The control condition runs on a machine/PATH
with no `aitp` binary.

## Seeds (`seeds/`)

Each scenario has one portable seed: a complete, self-contained workspace
fixture (`TOPIC.md`, Entries, Notes, pinned local files). The operator
copies it fresh into the isolated run workspace per condition per run; a run
never mutates the seed.

- **Window rule (active Entries).** A seed holds ≥ 28 **active** Entries —
  more than `enter`'s top-20 recent window, which is counted on active
  Entries only (`enter` orders active Entries by `created_at` desc;
  superseded Entries are excluded from the count and the window). At least
  one decisive memory-gated fact lives in an active Entry ranked outside
  the top-20, so reading the window alone cannot surface it. Retrieval must
  go through `rg` and direct file reads — the M0.6 retrieval path.
  `list`/`show` are M1a features; the M0.6 suite must not assume them.
- **Fixture validity.** Every fixture Entry/Note is valid v0.1 Markdown that
  passes the runtime validator, with fixed IDs and timestamps (byte-stable
  across runs), complete `refs`/`limitations`/body, and real sha256 pins to
  local files inside the seed. Filler records carry no `next_action`: the
  seeded `next_action` must come only from the intended record, so `enter`'s
  projection cannot be hijacked by a filler.
- **Evidence boundary.** Refs pin local files inside the seed only — no
  remote or unverifiable references, no pointer to anything outside the run
  workspace. Retrieval is `rg` over Markdown; the suite adds no index,
  cache, or daemon.
- **Gold separation.** Gold never enters a seed or any agent-readable run
  environment. `gold/` stays assessor-side; hosting it in the repo is fine.

## Scenario anatomy

Each scenario file contains:

1. **Seed reference**: the scenario names its seed under `seeds/` (see
   Seeds above for the fixture contract).
2. **Hidden facts**: 3–5 seeded facts unknown to the agent that a correct
   memory read must surface. At least one must *change a concrete action* in
   the session (e.g., a decisive past failure that rules out the otherwise
   natural next step), and it must sit outside `enter`'s top-20 window.
3. **Script**: the operator's user turns, verbatim, including:
   - an implicit durable event (a result/decision reached in conversation,
     not announced as "please record this");
   - an explicit non-durable distractor (chit-chat or a discarded idea that
     must NOT be recorded);
   - a correction whose value only becomes visible in a later turn/session.
4. **Probes**: the points where the assessor checks behavior (does the
   proposal cite the decisive record and its evidence locator? does the
   closeout use the right record type?).

`gold/` holds, per scenario: the hidden-fact answers, the expected action
change, and the typed durable-event list. Gold never enters a seed or the
agent-readable run environment; assessors score blind to condition
(treatment vs control order randomized, transcripts anonymized by the
operator).

## Turn-time event artifacts (`events/`)

Script turns can announce durable events that records must pin (S2 turns 4
and 5: L=64 entropy result, bond=600 memory failure). The physical trace of
such an event is a turn-time artifact: a small file whose canonical bytes are
committed under `events/<scenario>/` and whose digest is fixed in the
scenario. The operator copies it by hand into the run workspace at its pinned
path immediately before the script turn that announces the event — never
earlier, never in a seed, never at deploy time.

- **Scenario event evidence, not a harness.** Injection is a manual operator
  action (`cp -a` by hand) at a script turn: zero runtime lines, no script,
  hook, or harness — consistent with the human-executed design. The artifact
  is the event's physical trace: it is what the record's `sha256:` ref pins,
  and what the assessor verifies when checking the record (S2 probes P3/P4).
  It carries no information beyond the turn text, which names the file's
  path so the agent can open and pin it.
- **Not a condition difference.** The same canonical bytes are injected at
  the same turn, by the same procedure, in both conditions; the recorded
  target sha256 must be equal across conditions and equal to the scenario's
  fixed digest. The only intended difference between conditions remains the
  I/O adapter.
- **Recorded injection.** Before the turn is sent, the operator records the
  canonical source sha256, the workspace target sha256 (must equal the
  source), and the injection wall-clock in the run notes; the user turn is
  sent only after the injection.
- **Anti-leak.** An artifact must never exist in a workspace before its
  turn: never pre-seeded (step 1 checks the event paths are absent from the
  seed), never deployed at step 2, never injected before the previous turn's
  reply completed. A pre-seeded artifact leaks the event before it is
  announced; an artifact visible early, or divergent target digests between
  the conditions, voids the dependent probes.
- **Persistence.** After its turn the artifact stays in the workspace:
  end-state snapshots and session-2 replication carry it unchanged; it is
  evidence, not transient state (unlike `.aitp/local/`).
- **Inventory.** The per-scenario event inventory (canonical file → pinned
  workspace path, fixed digest, exact commands) is declared in the scenario's
  Event injection section and is part of the frozen scenario material.

## Run protocol (human-executed)

- The operator prepares each run: copies the scenario's portable seed into a
  fresh isolated workspace, adds the byte-identical `policy.md` plus the
  condition's adapter appendix, and archives the session under
  `suite/runs/<date>/` (gitignored).
- **Freeze record.** Before the first scored run the operator verifies
  `FROZEN.md`, the freeze record of everything fixed for scored runs: rubric
  thresholds (`rubric.md`), canonical seed bytes, scenario scripts and
  probes, event artifacts (`events/`), adapters, the agent config (model,
  system prompt) once set, the runtime/test baseline, and the S3 hold-out.
  An unfrozen item voids the run as the first scored run and must be
  resolved and recorded in the stage notes before scoring.
- **Record templates.** `run-notes-template.md` and `score-sheet-template.md`
  are documentation templates, not tooling: the operator copies the run-notes
  template into `suite/runs/<date>/<scenario>/` and fills every hash/path
  placeholder by hand as the run proceeds; the assessor copies the
  score-sheet template before scoring and fills it in by hand. No script,
  hook, or harness reads or generates them.
- **Isolation**: the agent under test can see only that workspace,
  `policy.md`, and its condition's adapter — never the repo, scenarios,
  seeds, gold, or rubric.
- **Parity**: treatment and control use the same model, the same fixed
  prompt/agent config (frozen before the run), identical copies of the same
  seed, and identical budgets; the only difference is the I/O adapter (AITP
  CLI vs plain files). Any measured difference is attributed to the full
  AITP I/O layer — commands, validation, `enter` projection, template
  mechanics — not to policy content or template wording.
- **Turn-time event artifacts**: at each scenario-declared event turn the
  operator injects the canonical artifact by hand into both workspaces,
  immediately before sending the turn, and records source/target sha256 and
  the injection time in the run notes (see Turn-time event artifacts above;
  per-scenario inventory in the scenario's Event injection section). Never
  pre-seeded, never a harness, never a condition difference.
- The operator executes the scripted turns verbatim (the agent-visible user
  message per turn is exactly the scripted turn text; operator instructions —
  budget, boundary, CLI path, framing — are delivered outside the
  conversation or fixed pre-run, never per-turn), ends the run at the
  declared budget with a recorded budget-stop marker, archives the raw
  transcript untouched (anonymization happens only in packet extraction,
  never in the transcript), and randomizes condition order. Gold is visible
  only to the assessor, after the run.
- **Fresh resumption**: a resumption probe is a fresh session (new
  conversation, new agent process) started from a fresh copy of the
  scenario's end-state workspace, with the same `policy.md` + adapter and no
  transcript of the earlier session — the ledger is the only continuity
  mechanism.

## Scored-run protocol clarifications (from the unscored 2026-08-06 dry run)

Binding for scored runs; none change a threshold, seed, script text, gold
answer, or event artifact:

- **Operator-owned authoritative transcript.** The transcript is the raw
  chat/tool log the agent harness captures, archived untouched — never
  agent-authored, agent-summarized, or agent-read. Per script turn it records
  the exact delivered user message, the agent's full reply output, UTC
  `TURN_START`/`TURN_END` (ISO 8601), the cumulative tool-call count, and the
  `FIRST_GROUNDED_PROPOSAL` marker. It is the only source for the budget
  counter, M5, and packet extraction.
- **Verbatim delivery.** The agent-visible user message per turn is exactly
  the scripted turn text; operator instructions (budget, boundary, CLI path,
  framing) are delivered outside the conversation or fixed pre-run in the
  environment/adapter, never as per-turn wrapper text. A wrapped turn voids
  the probes it could have leaked.
- **Identity pre-recorded (mandatory).** Before the run, the run notes record
  model id, provider/endpoint, model version, system prompt sha256 (plus
  developer prompt sha256 if separate), agent config sha256 + inventory,
  harness/CLI client version, adapter hashes, the treatment launcher
  absolute path + sha256 and interpreter path + `python --version` output
  (the CLI has no `--version` flag), the installed plugin manifest `version`
  field + manifest sha256, Skill hashes and the Skill
  policy decision (identical in both conditions, or treatment-only
  `aitp`/`using-aitp` Skills as part of its adapter envelope), and the
  canonical runtime revision (repo commit or working-tree hash; plus the
  `scripts/vendor/aitp/` tree hash as exercised). Any identity
  difference between conditions — or any field left unrecorded — voids the
  run.
- **Budget enforcement.** The tool-call budget (40 calls, all three
  scenarios) is counted by the operator from the authoritative transcript
  under one fixed rule in both conditions. At the first reply completion
  at-or-after the budget, the session stops (no further turns are sent) and
  a budget-stop marker (UTC, turn, cumulative count) is recorded; the session
  is marked `budget-exceeded` (invalid as script-complete). Per the frozen
  rubric, exceeding a budget ends the session and scores what exists — a
  recorded session-end event, not a void condition.
- **M5 requires instrumentation.** M5 is unscorable without run-time turn
  timestamps and tool-call counts; missing instrumentation is a run-voiding
  condition and is never reconstructed post hoc.
- **M4 pre-registration.** The resumption script (verbatim prompt), its
  budget, and its session boundary (fresh agent process, fresh conversation,
  fresh `cp -a` copy of the end state, no session-1 transcript available) are
  fixed in the run notes before session 1 runs and stay frozen.
- **Blind review only.** Scored-run review happens only through independent
  condition-neutral blind packets; raw-transcript review is never part of a
  scored run.
- **Treatment preflight; control never calls AITP.** The treatment machine's
  exact CLI launcher and interpreter (Python ≥ 3.11) are verified and
  recorded pre-run per `adapters/cli.md`. The CLI has no `--version` flag;
  identity is recorded deterministically: launcher absolute path + sha256,
  interpreter absolute path + `python --version` output, installed plugin
  manifest `version` field + manifest sha256, canonical runtime
  revision/tree hash, and Skill hashes. The control machine has no `aitp`
  on `PATH` and nothing importable, and no control-session tool call invokes
  any AITP CLI.

## Metrics (rubric.md fixes these before the first run)

- **Hidden-fact action score**: fraction of hidden facts that surfaced AND
  changed the corresponding action with a citation to the decisive record
  and evidence locator. Running `enter` without using what it returns scores
  zero.
- **Typed durable-event recall / precision**: against the gold typed-event
  list. A single catch-all closeout covering heterogeneous events is scored
  as a type error, not as recall.
- **Non-durable rejection**: distractors recorded = penalty.
- **Resumption checklist**: on a fresh session seeded from the scenario's
  end state — current goal, active route, next action, open
  corrections — each item checkable against the records.
- **Cold-start metrics**: time and tool calls from session start to the
  first grounded proposal, per condition.

Pre-registered thresholds live in `rubric.md` and are frozen before the
first scored run; they are not negotiated per stage. Initial values for the
M0.6 core run: hidden-fact action score ≥ 0.6 in the treatment condition AND
strictly above the control on the same scenarios; typed recall ≥ 0.7 with
precision ≥ 0.7; non-durable rejection 100%; resumption checklist ≥ 4/4.
Thresholds may only be revised between stage runs, with the diff recorded in
the stage notes.

## Anti-gaming rules (binding)

- Scores attach to outcomes (changed actions, correct types, citations), never
  to rituals (having run a command, having written a file).
- Seeds exceed the retrieval window by active count (≥ 28 active vs the
  top-20 window) and hide a decisive fact outside the top-20; mechanical
  "read the top N" fails.
- Assessor is blind to condition; agent never sees gold labels.
- Fixed per-session budgets (turns, tool calls) declared in the scenario;
  exceeding them ends the run and scores what exists.
- Scenario S3 is held out: prompts, Skills, and adapters may be iterated
  against S1/S2 only. Held-out means S3 is not used for prompt/Skill
  iteration once the agent config is frozen; structural repairs to the S3
  fixture before the first scored run (e.g., a broken pin or ID) are
  permitted but must be recorded in the stage notes with what changed and
  why — content repair, not iteration. S3 scores are reported separately and
  first.

## Explicitly out of scope

- No automated evaluation platform, LLM-judge pipeline, or CI integration at
  this stage. Human execution is the design, not a stopgap.
- No multi-agent or longitudinal tracking beyond the cold-start metrics.
- No scenario generation tooling; scenarios are hand-written from real
  dogfood material.
- No dependency on M1a retrieval commands (`list`/`show`) or any index:
  M0.6 retrieval is `rg` + direct file reads.
